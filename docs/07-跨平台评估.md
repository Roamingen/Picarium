# 07 · 跨平台评估：macOS 与 iOS

> 2026-10-28 · 回答「以后加 macOS/iOS 要不要重写」

---

## 1. 结论先说

| 平台 | 要重写吗 | 工作量 | 主要成本 |
|---|---|---|---|
| **macOS** | **不需要**。改壳 + 改路径 + 重新打包 | **5–8 人日** | 签名/公证、少量窗口行为差异 |
| **iOS** | **不需要重写核心**，但交互模型不同，要新做一个「分享扩展」壳 | **15–20 人日** | Xcode 工程、App Group、Apple 开发者账号（$99/年） |

核心逻辑（库、索引、去重、搜索、同步）是纯 Rust，**一行都不用改**。

---

## 2. 为什么能复用

现在的分层：

```
app/src/main.rs     ← 平台相关：托盘、全局热键、窗口  （约 250 行）
app/ui/*            ← 纯 Web，天然跨平台
crates/core/*       ← 纯 Rust：只碰文件系统和内存，零平台 API
```

`crates/core` 的依赖只有 `serde / serde_json / sha2 / walkdir / anyhow / chrono / image`，全是跨平台的。
**它不知道自己在 Windows 上跑。**

剪贴板用的是 `arboard`（Windows/macOS/Linux 都支持），热键和托盘用的是 Tauri 官方插件（也跨平台）。所以：

| 层 | Windows | macOS | iOS |
|---|---|---|---|
| core | ✅ | ✅ 原样 | ✅ 原样 |
| 数据格式 | ✅ | ✅ | ✅ |
| UI | ✅ | ✅ 基本原样 | ⚠️ 要重排（手机布局） |
| 壳 | ✅ | 重写 ~200 行 | 重写 + 分享扩展 |
| 集成 | 剪贴板/热键/托盘 | 剪贴板/热键/菜单栏 | 分享扩展（没有热键） |

---

## 3. macOS 要改什么

| 项 | 具体情况 |
|---|---|
| 库路径 | `%USERPROFILE%\StickerBox` → `~/StickerBox` 或 `~/Library/Application Support/StickerBox`。`candidate_roots()` 加一个 `HOME` 分支即可 |
| 托盘 | 变成菜单栏图标（Tauri 同一个 API，样式不同） |
| 全局热键 | `Cmd+Option+Space`，插件支持；**不需要**辅助功能权限 |
| 复制图片 | `arboard` 写 NSPasteboard（PNG/TIFF），微信/QQ Mac 版 `Cmd+V` 正常 |
| 自动粘贴回写 | 要模拟 `Cmd+V`，**需要「辅助功能」授权**（和 Windows 的焦点还原一样，属于可选功能） |
| 打包 | `.app` + 代码签名 + 公证。个人自用可以 ad-hoc 签名（会有「无法验证开发者」提示）；公开分发要 Apple 开发者账号 |
| 窗口 | 无边框面板在 macOS 上表现略有差异（阴影、圆角），需要微调 |

**结论**：macOS 是一个「换壳 + 改路径 + 打包」的活，核心和 UI 不动。

---

## 4. iOS 为什么不能照搬

iOS 上没有这些东西：

| 能力 | iOS |
|---|---|
| 全局热键 | ❌ 不存在 |
| 常驻托盘 | ❌ 进程随时被杀 |
| 后台监听剪贴板 | ❌ 系统禁止 |
| 任意文件系统访问 | ❌ 沙盒 + 照片库授权 |
| 应用间拖拽 | ⚠️ 仅部分场景 |

所以 iOS 的形态只能是：

```
收：微信/相册 → 分享 → StickerBox（Share Extension，不打开主 App 也能存）
看：打开 App 浏览、搜索
发：选图 → 分享 → 微信（以图片发送）
```

**「快贴」在 iOS 上不成立**——没有系统级唤起，只能「打开 App → 选 → 分享」，比 Android 还多一步。
这也是我不建议现在做 iOS 的原因：投入最大，体验最弱。

技术上，Tauri 2 支持 iOS，但需要：

1. 用 Xcode 建一个 Share Extension（Swift，约 300 行）；
2. App Group 让扩展和主 App 共享库目录；
3. Rust 核心编译成 iOS 静态库（`aarch64-apple-ios`）；
4. 真机调试和分发都要 Apple 开发者账号。

---

## 5. 如果真要做，顺序建议

1. **macOS**（5–8 人日）：验证核心跨平台没坑，成本低、体验几乎无损；
2. **iOS**（15–20 人日）：等 Android 版跑顺、确认「手机端只做收/看/发」这套模型成立之后，再复制到 iOS。

---

## 6. 现在就要为跨平台做的准备（都是零成本）

| 现在做 | 目的 |
|---|---|
| 路径全部走 `candidate_roots()`，不硬编码盘符 | macOS 只需加 `HOME` 分支 |
| 平台相关代码只放 `app/src/main.rs` | 换平台时只改一个文件 |
| 库里不写绝对路径（索引里的 `path` 每次由根目录重算） | 库可以跨机器、跨系统搬 |
| ops 日志与 blobs 不含平台信息 | 同步天然跨平台 |
| UI 不依赖任何 Windows 字体/控件 | 换到 WKWebView 直接能跑 |

这几条现在已经做到了，所以将来加 macOS 不是「重构」，是「接一个壳」。
