# 14 · 数据结构与演进

> 2026-10-29 · 现在存了什么、为什么这么存、什么时候该换数据库

---

## 1. 库的物理结构

```
Picarium/
├── index.json          # 唯一的索引：所有表情的元信息
├── blobs/ab/cd/<sha>.<ext>      # 原始文件，内容寻址（ab/cd 是 sha 前 4 位分桶）
├── thumbs/ab/cd/<sha>.jpg|webp  # 缩略图，可删可重建
├── trash/
│   ├── index.json      # 回收站清单（含完整元信息 + 删除时间）
│   └── <sha>.<ext>     # 被删文件的实体
├── exports/            # 预留：导出
└── inbox/              # 预留：收件箱
```

**核心原则：文件是真身，索引是缓存。** 删掉 `index.json` 和 `thumbs/`，数据仍然在 `blobs/` 里，只是名字和标签会丢——所以后面才要做"从 blobs 重建"。

## 2. index.json 的结构

```json
{
  "version": 1,
  "seen_ungrouped_at": "2026-10-29T12:00:00+00:00",
  "assets": [ { ...Asset... } ]
}
```

### Asset 字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `sha` | string | **内容指纹**，blobs 文件名、去重依据、缩略图主键 |
| `ext` | string | 扩展名（嗅探后写入，不信任原文件名） |
| `bytes` | number | 原始大小 |
| `width` / `height` | number | 像素尺寸（导入时读文件头） |
| `animated` | bool | 是否多帧（GIF / APNG / 动画 WebP），决定点击是复制文件还是位图 |
| `name` | string | 显示名，可改（默认取文件名） |
| `source` | string | `folder` / `clipboard` 等来源类别 |
| `source_ref` | string | 原始路径或进程名（如 `WeChat.exe`） |
| `added_at` / `used_at` | ISO 时间 | 导入时间 / 最近一次复制时间 |
| `tags` | string[] | 标签，多对多（按名字存，没有独立 tag 表） |
| `groups` | string[] | 所属分组，可多个 |
| `starred` | bool | 收藏 |
| `py` / `py_abbr` | string | 拼音全拼 / 首字母，导入和改名时算好 |
| `path` | string | 运行时由库根目录重算，不信任索引里的旧值 |

> `readings`（多音字读音表）**不落盘**，打开库时在内存里重建，几毫秒。

### trash/index.json

```json
[ { "asset": { ...同上... }, "deleted_at": "2026-10-29T..." } ]
```

保留完整元信息，所以恢复后标签、分组、收藏都还在。

**孤儿文件收养**：`trash/` 里文件名是 sha 的图片、但清单里没有（老版本「先清元数据再送系统回收站」失败、或用户从系统回收站还原回来）会在读取时自动收养为 `未命名-<sha前8>`，并把元数据写回。删除/清空时也是**文件处理成功后才移除清单条目**，避免出现「磁盘有文件、界面 0 张、到期也清不掉」。

## 3. 为什么现在不用数据库

| 规模 | index.json 大小 | 全量写入 | 判断 |
|---|---|---|---|
| 1 千张 | ~0.5 MB | ~5 ms | 无感 |
| 1 万张 | ~5 MB | ~30 ms | 可接受 |
| 5 万张 | ~25 MB | ~150 ms | 开始难受 |

现在每次增删改都会**全量重写** index.json（原子写：临时文件 + rename）。这是有意的简化：文件可读、可手改、能进 git、坏了能修。

真正需要上 SQLite 的信号：

1. 库超过 ~1 万张；
2. 需要多进程/多实例同时写（现在靠单实例锁规避）；
3. 需要复杂查询（多标签组合、范围筛选、全文检索排序）；
4. 需要增量写（不想每次重写 25 MB）。

## 4. 迁移路径（提前设计好，不急着做）

```
SQLite（WAL）：
  asset / tag / asset_tag / group / asset_group / trash / fts5
blobs 与 thumbs 原样不动
index.json 仅作为导出/备份格式保留
```

- 迁移时按 `sha` 去重（现在打开库已经会做，算一次预演）；
- 检索从"内存过滤"换成 SQL + FTS5（trigram，中文子串可搜）；
- 同步协议不受影响：blobs + ops 日志与索引实现无关。

## 4.5 设置文件 settings.json（全局配置，不在库里）

设置、自定义主题、库指针放在**全局配置目录**，换库 / 搬库都不丢：

```
%APPDATA%\Picarium\config.json     // 库指针 + 最近库
%APPDATA%\Picarium\settings.json   // 全部用户偏好
%APPDATA%\Picarium\themes\*.json   // 自定义主题
```

- 环境变量 `PICARIUM_CONFIG_HOME` 可覆盖配置目录（测试脚本必须设置，避免污染真实配置）；
- 旧版本的库根 `settings.json` / `themes/` 在首次升级时**复制**到配置目录，库里原文件保留（旧版本可回退）；复制失败则继续用旧布局；
- 安卓：配置目录是应用私有目录下的 `PicariumConfig`，同样与库分开。

字段（都在全局 settings.json 里）：

```json
{
  "theme": "dark",             // dark | light | catppuccin-* | 自定义 themes/<id>.json
  "starStyle": "heart",      // heart | star（早期版本存的是 ♥/★，会自动迁移）
  "starColor": "#f5b301",
  "hoverDelay": 350,          // 悬停多少毫秒播放动图，0 = 关闭
  "deleteMode": "recycle",    // recycle | permanent
  "ghostX": 4,
  "ghostY": 4,
  "clipboardEnabled": true,
  "autostart": false,
  "gridSize": "normal",
  "copyDefault": "bitmap",
  "startHidden": false,
  "startView": "all",          // all | recent | star | ungrouped | group:<名字>
  "windowWidth": 1040,
  "windowHeight": 700,
  "panelWidth": 720,
  "panelHeight": 520,
  "panelX": 0,
  "panelY": 0,
  "panelSort": "recent",       // recent | name | added
  "recentLimit": 60,           // 快贴面板最多显示多少条
  "virtualize": true,          // 只渲染可见卡片（默认开）
  "clipboardBlacklist": ["snipaste.exe"], // 剪贴板黑名单（进程名）
  "filters": {                 // 高级筛选（全局）
    "minBytes": 0, "maxBytes": 0,
    "minWidth": 0, "maxWidth": 0,
    "minHeight": 0, "maxHeight": 0,
    "exts": [], "tags": [],
    "sourceKeys": [], "presets": [],
    "from": "", "to": ""
  }
}
```

缺字段用默认值，同步升级不会因为多一个字段就报错；导入导出就是整份 JSON。

## 5. 一致性与并发

| 问题 | 现在的做法 |
|---|---|
| 两个实例同时写 | **端口单实例锁**（127.0.0.1:47821） |
| 写一半崩溃 | 临时文件 + 原子 rename |
| 多个线程读写 | `Mutex<Library>`，导入时**逐文件加锁**，不长时间占用 |
| 同一内容多条记录 | 打开库时按 sha 强制去重；恢复时若已存在则合并元信息 |
| 幽灵记录（文件没了） | 打开库时清理，避免空卡片 |

## 6. 已知限制

1. **全量重写**：每次改动都写整个 index.json，几万张时会明显变慢（见第 3 节迁移信号）。
2. **sha 没有数据库级唯一约束**：靠打开时去重 + 恢复时检查，属于"软约束"。
3. **没有操作日志**：将来做多端同步需要补 `ops/` 追加日志（设计已在 `docs/02` 里）。
4. **标签没有独立表**：改名/合并标签要遍历所有 asset（几千张没问题，几万张要慎重）。
