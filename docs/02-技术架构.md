│   │ 原生薄壳      │  托盘/热键/剪贴板/分享意图         │  核心引擎  │  │
│   │ Win: pywebview│                                 │ 索引/搜索/ │  │
│   │ Android: Cap │                                  │ 分类/同步  │  │

│                                              ┌───────────▼──────┐ │

                                                           │

**核心思路：把「界面」和「能力」拆开，界面是纯 Web，能力是本地 HTTP 服务。**
这样 Windows 和 Android 共用一份 UI，各自只写一层薄薄的原生壳去接系统能力（热键、托盘、剪贴板、分享意图、媒体库）。

## 2. 技术选型

### 2.1 桌面端对比

| 方案 | 开发速度 | 安装包 | 常驻内存 | 热键/托盘 | 与 Android 复用 | 图像/AI 生态 | 结论 |
|---|---|---|---|---|---|---|---|
| **Python + WebView** | ★★★★★ | 60–90 MB | 150–300 MB | ★★★★（pywin32） | 中（UI 复用） | ★★★★★（Pillow/OCR/ONNX） | ✅ **推荐** |
| Electron | ★★★★ | 150 MB+ | 300 MB+ | ★★★★ | 高（UI 复用） | ★★★（Node ONNX） | 备选 |
| Tauri 2 | ★★★ | 10–20 MB | 80 MB | ★★★★ | 最高（同栈还能编 Android） | ★★★（Rust + ort） | 备选（想单栈时） |
| Flutter | ★★★ | 40 MB | 200 MB | ★★★ | 最高（真同栈） | ★★★★ | 备选 |
| C# / WPF | ★★★★ | 40 MB | 120 MB | ★★★★★ | 低 | ★★★★ | 只做纯 Windows 时选 |

**选 Python 的理由**

1. 你这台机器已有 Python 3.12.4，改一行就能跑，调试链路最短（没有编译、没有打包）。
2. OCR（RapidOCR）、感知哈希（imagehash）、图像处理（Pillow）、CLIP（onnxruntime）在 Python 里全是现成的，换成 Rust/Node 都要重新踩一遍。
3. 表情包管理的性能瓶颈在「解码 + 生成缩略图」，Python 调 C 库（Pillow/OpenCV）完全够用，纯 Python 的部分只做调度。

**选 Python 的代价与缓解**

| 代价 | 缓解 |
|---|---|
| PyInstaller 打包 60–90 MB、首启稍慢 | 日常用 `run.bat` 从源码跑（秒开）；只在送人时打包 |
| 全局热键库（`keyboard`）常被杀软误报 | 直接用 `ctypes` 调 `RegisterHotKey`，不依赖第三方库 |
| 无边框置顶窗口观感一般 | pywebview(WebView2) 足够；不满意再换 Tauri 只换壳，后端不动 |

### 2.2 移动端选型

| 方案 | 分享接收 | 媒体库访问 | UI 复用 | 调试体验 | 结论 |
|---|---|---|---|---|---|
| **Capacitor + Kotlin 插件** | ✅ Intent Filter | ✅ 原生插件 | ✅ 复用 SPA | 一般（WebView 可远程调试） | ✅ **推荐** |
| 纯 Kotlin + Compose | ✅ | ✅ | ❌ 重写 | 好 | UI 性能兜底方案 |
| Flutter | ✅ | ✅ | ❌ 重写 | 中 | 不选（与桌面不同栈） |
| PWA（Web Share Target） | ⚠️ 需 HTTPS + 安装 | ❌ 不能扫相册 | ✅ | 好 | 不满足需求 |

**关键点**：Android 端**不追求功能对等**，只做三件事——收图、找图、发图，外加一个「相册体检」。所以 UI 复用是划算的，复杂管理仍在 Windows 上做。

### 2.3 语言与运行时清单

| 组件 | 选型 | 版本基线 |
|---|---|---|
| 桌面后端 | Python 3.12 + FastAPI + Uvicorn | 已有 |
| 数据库 | SQLite 3.45+（WAL，FTS5） | Python 自带 |
| 图像 | Pillow 10+ | |

| OCR | RapidOCR（PP-OCRv4 ONNX，约 15 MB） | |

## 3. 库格式

### 3.1 目录结构

```
Picarium/
├── library.json              # 库标识：id / schema 版本 / 创建时间
├── library.db                # SQLite 索引（不同步，可重建）
├── blobs/
│   └── a3/
│       └── f1/
│           └── a3f1...c9.png # 文件名 = SHA-256，不可变
├── thumbs/
│   └── a3/f1/a3f1...c9.webp  # 512px 缩略图（不同步，可重建）
├── ops/                      # 同步日志（追加写）
│   ├── pc-8f2a/
│   │   └── 00000001.jsonl
│   └── phone-3c91/
│       └── 00000001.jsonl
├── inbox/                    # 收件箱：丢文件进去自动入库
├── trash/                    # 回收站：软删 30 天
└── exports/                  # 导出产物
```

### 3.2 规则

| 规则 | 原因 |
|---|---|
| `blobs/` 下文件**只增不改**，内容寻址 | 同步永不冲突；天然去重；损坏可校验 |
| 扩展名按**嗅探**结果写，不信任原文件名 | 微信/QQ 文件常无扩展名或扩展名错误 |
| 缩略图**可随时删除**，懒重建 | 省同步流量，省备份体积 |
| `library.db` **不参与同步** | SQLite 双写必炸；索引本就可重建 |
| 所有用户操作**先写 ops，再改 db** | 崩溃后能靠日志补齐 |
| 回收站保留 30 天，且**不删 ops** | 误删可恢复；ops 很小，留着没负担 |

### 3.3 判定「这是不是 Picarium 库」

读 `library.json` → 有 `id` 和 `schema` → 是。没有就拒绝打开，避免误伤普通文件夹。

## 4. 数据模型

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA foreign_keys = ON;

CREATE TABLE meta (k TEXT PRIMARY KEY, v TEXT);

-- ---------- 资产 ----------
CREATE TABLE asset (
  sha256        TEXT PRIMARY KEY,          -- 内容寻址主键
  ext           TEXT NOT NULL,             -- png/jpg/gif/webp/mp4
  mime          TEXT NOT NULL,
  bytes         INTEGER NOT NULL,
  width         INTEGER,
  height        INTEGER,
  frames        INTEGER NOT NULL DEFAULT 1,
  animated      INTEGER NOT NULL DEFAULT 0,
  duration_ms   INTEGER,
  phash         TEXT,                      -- 64bit 感知哈希（hex）
  sticker_score REAL,                      -- 0..1
  kind          TEXT NOT NULL DEFAULT 'unknown', -- sticker|photo|screenshot|meme|other
  source        TEXT,                      -- qq_pc|wechat_pc|clipboard|android_share|album|folder
  source_ref    TEXT,                      -- 原始路径 / 包名 / 群名
  captured_at   TEXT,                      -- 源文件时间
  imported_at   TEXT NOT NULL,
  used_at       TEXT,
  use_count     INTEGER NOT NULL DEFAULT 0,
  starred       INTEGER NOT NULL DEFAULT 0,
  deleted_at    TEXT                       -- 非 NULL 即在回收站
);
CREATE INDEX idx_asset_kind     ON asset(kind)     WHERE deleted_at IS NULL;
CREATE INDEX idx_asset_imported ON asset(imported_at);
CREATE INDEX idx_asset_phash    ON asset(phash);

-- ---------- 标签 ----------
CREATE TABLE tag (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  kind  TEXT NOT NULL DEFAULT 'user',      -- user|auto|system
  color TEXT,
  UNIQUE(name, kind)
);

CREATE TABLE asset_tag (
  sha256     TEXT NOT NULL REFERENCES asset(sha256) ON DELETE CASCADE,
  tag_id     INTEGER NOT NULL REFERENCES tag(id) ON DELETE CASCADE,
  origin     TEXT NOT NULL DEFAULT 'user', -- user|auto
  confidence REAL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (sha256, tag_id, origin)
);

-- ---------- 文本 / 全文索引 ----------
CREATE TABLE asset_text (
  sha256    TEXT PRIMARY KEY REFERENCES asset(sha256) ON DELETE CASCADE,
  ocr       TEXT,
  ocr_lang  TEXT,
  updated_at TEXT
);
CREATE VIRTUAL TABLE asset_fts USING fts5(
  sha256 UNINDEXED, ocr, tags, filename,
  tokenize = 'unicode61 remove_diacritics 0'
);

-- ---------- 合集 ----------
CREATE TABLE collection (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, cover_sha TEXT, sort INTEGER DEFAULT 0
);
CREATE TABLE collection_asset (
  collection_id INTEGER NOT NULL REFERENCES collection(id) ON DELETE CASCADE,
  sha256 TEXT NOT NULL REFERENCES asset(sha256) ON DELETE CASCADE,
  sort INTEGER DEFAULT 0,
  PRIMARY KEY (collection_id, sha256)
);

-- ---------- 语义向量（P2） ----------
CREATE TABLE embedding (
  sha256 TEXT PRIMARY KEY REFERENCES asset(sha256) ON DELETE CASCADE,
  model TEXT NOT NULL, dim INTEGER NOT NULL, vec BLOB NOT NULL
);

-- ---------- 同步幂等 ----------
CREATE TABLE applied_op (
  dev TEXT NOT NULL, seq INTEGER NOT NULL, applied_at TEXT NOT NULL,
  PRIMARY KEY (dev, seq)
);

-- ---------- 任务队列 ----------
CREATE TABLE job (
  id TEXT PRIMARY KEY, kind TEXT NOT NULL, state TEXT NOT NULL,
  total INTEGER, done INTEGER, error TEXT,
  created_at TEXT, updated_at TEXT
);
```

**为什么 SHA-256 当主键而不是自增 ID**：跨设备合并时不需要映射表；同一张图在两端天然是同一行；同步逻辑从「一堆 ID 映射」变成「集合求并」。

## 5. 索引流水线

### 5.1 阶段

```
发现文件
   │
   ├─▶ L1 去重：算 SHA-256 ── 已存在？→ 记一次「来源重复」直接结束
   │
   ├─▶ L2 落盘：blobs/ab/cd/<sha>.<ext>（先写临时文件再原子 rename）
   │
   ├─▶ L3 探测：mimetypes + Pillow 解析宽高/帧数/动画
   │
   ├─▶ L4 缩略图：长边 512 WebP q=80（动图取首帧 + 动图角标）
   │
   ├─▶ L5 感知哈希：pHash 64bit
   │
   ├─▶ L6 判别：启发式 sticker_score → kind
   │
   ├─▶ L7 OCR：RapidOCR（只有 L6 判为 sticker/meme 的才跑，省一半时间）
   │
   └─▶ L8 向量：CLIP（可选，后台慢慢跑）
```

**分级策略**：L1–L6 在导入时同步完成（用户可感知的延迟 < 1 ms/张）；L7–L8 进后台队列，可暂停、可限速、可只跑「未整理」。

### 5.2 状态机

```
pending → stored → thumbnailed → scored → ocr_done → embedded
                     └──────────────┴────────► failed（可重试）
```

用 `job` 表 + 单写线程消费，避免并发写 SQLite 造成 `database is locked`。

### 5.3 增量与重扫

- 增量靠 `source_ref`（原始绝对路径）+ 文件大小/修改时间，避免每次全量哈希。
- `POST /api/maintenance/rebuild` 只重建索引不碰 blobs，用于换机或修库。

## 6. API 契约

两端实现同一套路径，前端不需要知道自己在哪个平台。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 存活探测 |
| GET | `/api/stats` | 数量/占用/格式分布/待整理数 |
| GET | `/api/assets` | `q,tag,kind,source,animated,starred,sort,cursor,limit` |
| GET | `/api/assets/{sha}` | 详情（含标签、来源、相似图） |
| GET | `/api/assets/{sha}/raw` | 原图，支持 Range（动图播放必需） |
| GET | `/api/assets/{sha}/thumb?size=256` | 缩略图 |
| PATCH | `/api/assets/{sha}` | 改 starred / 增删标签 |
| POST | `/api/assets/{sha}/use` | 记录一次使用（影响排序） |
| POST | `/api/assets/{sha}/copy` | 写系统剪贴板（桌面专有，移动端返回 501） |
| DELETE | `/api/assets/{sha}` | 软删进回收站 |
| POST | `/api/assets/batch` | 批量：打标 / 收藏 / 删除 / 移入合集 |
| GET | `/api/tags` | 标签树（含计数） |
| POST | `/api/tags` | 新建/重命名/合并 |
| GET | `/api/import/sources` | 探测本机可导入源（QQ/微信/相册） |
| POST | `/api/import/scan` | 启动扫描任务 → 返回 `job_id` |
| POST | `/api/import/upload` | multipart 上传（移动端分享用） |
| GET | `/api/jobs/{id}` | 任务进度（SSE 或轮询） |
| POST | `/api/maintenance/{rebuild\|dedupe\|gc}` | 维护 |
| GET | `/api/sync/status` | 同步状态 |
| POST | `/api/sync/apply` | 应用一批 ops（移动端拉取时用） |

**约定**

- 分页用 **cursor**（`imported_at + sha256` 复合游标），不用 offset——5000 张翻到后面时 offset 会明显变慢。
- 所有写操作返回**完整的新对象**，前端不做乐观合并，减少状态 bug。
- 长任务一律异步：先返回 `job_id`，再轮询，避免 HTTP 超时。

## 7. 搜索设计

### 7.1 三层

| 层 | 技术 | 覆盖 | 延迟 |
|---|---|---|---|
| 精确/前缀 | SQL `LIKE` + 索引 | 文件名、标签名 | < 5 ms |
| 全文 | FTS5 + 分词 | OCR 文本、标签、备注 | < 20 ms |
| 语义 | CLIP 向量 + 余弦（sqlite-vec 或内存暴力） | 「猫很无语」这类描述 | 50–200 ms（5000 张可暴力扫） |

### 7.2 中文分词

- 写入 FTS 前对 OCR 文本做 **jieba 分词**，用空格连接，例如「我真的无语了」→「我 真的 无语 了」。
- 用 `unicode61` 分词器，单字也能建索引，2 字查询可用。
- 2 字以下的模糊查询走 `LIKE '%x%'` 兜底（5000 行全表扫也就几毫秒）。

> 备选：`tokenize='trigram'`（SQLite ≥ 3.34）。优点是子串天然可搜，缺点是查询短于 3 字符时用不上索引，且索引体积约为原文 3 倍。**先用 jieba 方案，M2 再评估 trigram。**

### 7.3 排序

`score = 0.45 × 文本相关度 + 0.35 × 使用频次衰减 + 0.15 × 收藏 + 0.05 × 新鲜度`

使用频次衰减：`count / (1 + days_since_last_use / 30)`。目的：常用表情越用越靠前，符合直觉。

## 8. 同步协议

### 8.1 为什么不直接同步 SQLite

SQLite 文件级同步在两端同时写入时必然冲突，Syncthing 会生成 `.sync-conflict-` 副本，恢复逻辑极其恶心。
**改成：不可变数据走文件同步，可变数据走追加日志，本地数据库永远只由本机写。**

### 8.2 三条流

| 流 | 内容 | 冲突可能 | 处理 |
|---|---|---|---|
| blobs | 内容寻址文件 | **不可能**（同名必同内容） | 直接覆盖/跳过 |
| ops | 每设备独立追加文件 | **不可能**（各写各的文件） | 按 (ts, dev, seq) 重放 |
| db / thumbs | 本机派生 | 不参与同步 | 排除 |

### 8.3 op 格式

每行一个 JSON，追加写 `ops/<dev>/<batch>.jsonl`：

```json
{"v":1,"dev":"pc-8f2a","seq":1041,"ts":"2026-10-28T21:30:12.431+08:00","op":"asset.add","sha":"a3f1…","data":{"ext":"png","bytes":48213,"w":300,"h":300,"source":"qq_pc"}}
{"v":1,"dev":"pc-8f2a","seq":1042,"ts":"2026-10-28T21:31:02.115+08:00","op":"tag.add","sha":"a3f1…","data":{"tag":"无语","origin":"user"}}
{"v":1,"dev":"pc-8f2a","seq":1043,"ts":"2026-10-28T21:35:44.002+08:00","op":"asset.star","sha":"a3f1…","data":{"on":true}}
{"v":1,"dev":"pc-8f2a","seq":1044,"ts":"2026-10-28T21:36:01.900+08:00","op":"asset.del","sha":"a3f1…"}
```

op 类型：`asset.add` `asset.del` `asset.restore` `asset.star` `asset.meta` `tag.add` `tag.del` `collection.add` `collection.del`。
**`use` 不同步**（纯本机行为，同步只会放大写放大）。

### 8.4 合并规则

| 场景 | 规则 |
|---|---|
| 同一 (dev, seq) 重复应用 | `applied_op` 主键去重，幂等 |
| 标量字段（star、kind） | Last-Writer-Wins，按 `ts` |
| 标签 | 按 (sha, tag, origin) 做 LWW；add/remove 各自带时间戳 |
| 删除 vs 恢复 | 时间戳晚者胜；删除后 30 天内可恢复 |
| 两端同时导入同一张图 | sha256 相同 → 天然合并为一行，两个来源都记录 |

> 用 LWW 而不是 CRDT，是因为这是**单人多设备**场景，真正的并发写几乎不会发生；即便发生，丢一次标签也无所谓。别为了理论优雅把复杂度翻三倍。

### 8.5 同步布局（Syncthing）

共享整个 `Picarium/`，忽略文件：

```
library.db
library.db-wal
library.db-shm
thumbs/
trash/
exports/
inbox/
.sync-conflict-*
```

- Syncthing 负责传输，不负责合并；合并发生在 App 启动时（重放未应用的 ops）。
- 首次同步：先传 blobs（大），再传 ops（小）。Syncthing 天然按需。
- 手机上 Syncthing 耗电，建议「仅在 Wi-Fi + 充电时同步」。

### 8.6 局域网直连（M4 备选）

```
手机                                  电脑
  │  GET /api/sync/manifest?since=1044  │
  │ ──────────────────────────────────▶ │
  │  { ops:[...], blobs:[sha...] }      │
  │ ◀────────────────────────────────── │
  │  GET /api/blobs/{sha}  (逐个拉)      │
  │ ──────────────────────────────────▶ │
```

够简单，但需要处理 mDNS 发现、配对、断点续传。**先别做**，等文件夹同步真的不够用再说。

## 9. 桌面壳实现要点

### 9.1 全局热键

```python
import ctypes
from ctypes import wintypes
MOD_ALT, MOD_CONTROL, MOD_NOREPEAT = 0x0001, 0x0002, 0x4000
VK_SPACE = 0x20

user32 = ctypes.windll.user32
if not user32.RegisterHotKey(None, 1, MOD_CONTROL | MOD_ALT | MOD_NOREPEAT, VK_SPACE):
    ...  # 被占用，提示换键
```

热键消息要在**独立的 GUI 线程**里 `GetMessage` 循环，不能和后端服务线程混。

### 9.2 快搜面板

- pywebview 创建 `frameless=True, on_top=True, width=680, height=420, resizable=False`
- 显示前：`GetForegroundWindow()` 存下 hwnd → `ShowWindow` → `SetForegroundWindow` → 前端 `input.focus()`
- 关闭：`Esc` 或失焦（前端 `blur` 事件 + 后端兜底）
- 背景：`transparent=True` + CSS 圆角阴影，观感接近 Spotlight

### 9.3 剪贴板写入（跨软件粘贴的关键）

一次写入三种格式，兼容性最好：

| 格式 | 用途 |
|---|---|
| `CF_DIB` | 微信/QQ 认这个（Ctrl+V 直接变图片） |
| 注册格式 `"PNG"` | 现代应用（浏览器、Discord、Slack） |
| `CF_HDROP` | 需要拖拽/贴文件路径的应用 |

注意：GIF/WebP 动图经剪贴板粘贴后**通常会退化成一帧静态图**，这是系统限制，不是 bug。想发动图，走「拖拽文件」或「分享」（Android 端 `ACTION_SEND` 保留原文件）。

### 9.4 自动粘贴（P2，可选）

```
选中 → 写剪贴板 → 隐藏面板 → SetForegroundWindow(原 hwnd) → SendInput(Ctrl+V)
```

风险：Windows 前台锁（foreground lock）可能让 `SetForegroundWindow` 失败；杀软可能拦 `SendInput`。所以做成**默认关闭**的选项，失败时自动降级为「已复制，请手动 Ctrl+V」。

### 9.5 单实例

命名互斥体 `Global\Picarium.Singleton`；第二次启动只唤起已有实例的面板。

## 10. Android 实现要点

### 10.1 分享接收

```xml
<activity android:name=".MainActivity" android:launchMode="singleTask">
  <intent-filter>
    <action android:name="android.intent.action.SEND" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:mimeType="image/*" />
  </intent-filter>
  <intent-filter>
    <action android:name="android.intent.action.SEND_MULTIPLE" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:mimeType="image/*" />
  </intent-filter>
</activity>
```

- `onNewIntent` 里取 `EXTRA_STREAM`（Uri），`contentResolver.openInputStream` 读字节 → 直接算 SHA-256 → 入库。
- 单张走「静默入库 + 通知栏提示」，多张走「确认页」。
- **不要申请 `MANAGE_EXTERNAL_STORAGE`**（HyperOS 会反复弹窗，且应用商店审核不过）。

### 10.2 相册批量移动（Android 11+）

```kotlin
val uris: List<Uri> = ...                       // 用户勾选的媒体
val pi = MediaStore.createWriteRequest(resolver, uris)
startIntentSenderForResult(pi.intentSender, REQ_MOVE, null, 0, 0, 0)

// 用户点「允许」后
uris.forEach { uri ->
    val cv = ContentValues().apply {
        put(MediaStore.MediaColumns.RELATIVE_PATH, "Pictures/Picarium")
        put(MediaStore.MediaColumns.IS_PENDING, 0)
    }
    resolver.update(uri, cv, null, null)
}
```

- `createWriteRequest` 一次传太多 Uri 会让系统授权弹窗卡很久，需**分批**（建议 ≤200/批）。
- 移动后文件不会消失，只是换了目录 → 相册主视图清净，微信发图时照样能选到。
- 保留原文件不删除，**只搬家不销毁**，符合「不静默改文件」原则。

### 10.3 端侧识别

- 先用**纯启发式**（见 `01` 第 6.3 节），Kotlin 直接实现，零依赖、零延迟。
- CLIP 模型（约 90 MB int8）作为可选下载，仅在「相册体检」时用一次，不常驻。

### 10.4 HyperOS 适配清单

| 问题 | 处理 |
|---|---|
| 后台被杀 | 同步用 `WorkManager` + 前台服务（带常驻通知），引导用户加白名单 |
| 自启动限制 | 首次启动引导页给「自启动」入口（`miui.intent.action.OP_AUTO_START`） |
| 分享面板里找不到 App | 确保 `intent-filter` 声明了 `image/*`，且 App 已启动过一次 |
| 保存目录混乱 | 统一 `Pictures/Picarium/`，在系统相册里显示为独立相册 |
| 深色模式 / 大字体 | 用系统主题变量，不做硬编码颜色 |

## 11. 导入适配器

| 适配器 | 路径 / 来源 | 实测 | 实现要点 |
|---|---|---|---|
| `qq_pc` | `Documents\Tencent Files\<uin>\nt_qq\nt_data\Emoji\{personal_emoji,emoji-recv}\**\*.{jpg,png,gif}` | ✅ 882 个明文 | 直接读字节；`marketface` 是表情包资源（color/gray 成对），默认跳过 |
| `wechat_pc` | `Documents\WeChat Files\<wxid>\FileStorage\CustomEmotion\<2hex>\<md5>` | ⚠️ 1464 个 `V1MMWX` 加密 | 见下 |
| `wechat_v4` | `Documents\xwechat_files\<wxid>_*\...`（布局待确认） | ❓ | 先做探测，不硬编码 |
| `folder` | 任意目录（递归） | ✅ | 按扩展名 + 魔数双重判断 |
| `clipboard` | 系统剪贴板 | ✅ | 只收图片，忽略文本 |
| `android_share` | `ACTION_SEND` | ✅ | 保留原始字节，不转码 |
| `android_album` | MediaStore | ✅ | 需要 `READ_MEDIA_IMAGES`（Android 13+） |

### 11.1 微信 `V1MMWX` 现状（实测）

```
偏移 0..5   "V1MMWX"          (6 字节魔数)
偏移 6..7   每文件不同的 2 字节，1464 个文件里只有 1024 种取值，且分布不均
偏移 8..    密文：高熵、无重复块、无固定周期、非 zlib
文件长度    与 16 无对齐关系 → 不是 ECB/CBC，可能是流式加密（CTR/ChaCha 类）
```

**结论**：这是真加密，不是简单的单字节 XOR 混淆。要读，得从 `Weixin.dll` 或进程内存里找密钥/算法。

**投入产出判断**：

| 方案 | 成本 | 风险 | 建议 |
|---|---|---|---|
| 逆向 `Weixin.dll` 找算法 | 2–5 天，且每次大版本可能重来 | 高 | ❌ 不做 |
| 读进程内存抓密钥（PyWxDump 思路） | 1–2 天 | 中（可能触发风控） | ⚠️ M5 实验 |
| 不读文件，靠剪贴板/分享慢慢收 | 0 | 无 | ✅ **主路径** |
| 微信自带「另存为」逐张导出 | 1464 次点击 | 无 | 🟡 只用于补关键几十张 |

> 产品上把微信导入标注为「实验性，随时可能失效」，且**永远不放进 M1 的验收标准里**。

### 11.2 QQ 写回（可选）

QQ 的 `personal_emoji/Ori/` 是明文，理论上**丢文件进去**就可能被识别（QQ 是否扫描该目录待验证）。即使不行，也还有剪贴板这条路。所以「写回」只作为 M5 的加分项。

## 12. 性能预算

目标库规模：**5000 张，平均 150 KB，合计约 750 MB**。

| 项 | 预算 | 依据 |
|---|---|---|
| 首次索引（L1–L6） | 2–5 分钟 | 解码+缩略图约 40 ms/张，4 线程并行 |
| OCR 全量（L7） | 8–15 分钟 | RapidOCR CPU 约 120 ms/张 |
| CLIP 全量（L8） | 6–10 分钟 | ViT-B/16 CPU 约 80 ms/张 |
| 冷启动到可搜索 | < 2 s | 只开 DB + 首屏 200 条 |
| 快搜面板唤起 | < 150 ms | 预热窗口，隐藏而非销毁 |
| 搜索响应（FTS） | < 20 ms | 5000 行 |
| 网格滚动 | 60 fps | 虚拟滚动，DOM 节点 < 100 |
| DB 体积 | 20–40 MB | 索引 + OCR 文本 |
| 缩略图体积 | 80–120 MB | 5000 × 20 KB |
| 常驻内存 | 150–300 MB | Python + WebView2 |

**容量预估**：1 万张时，库约 1.5 GB（含缩略图），索引时间翻倍，仍然可接受。真正会先崩的是「一次性渲染」，所以虚拟滚动是硬要求。

## 14. 安全与隐私

| 原则 | 落实 |
|---|---|
| 零上云 | 除用户自己选的同步目录外，不发起任何外网请求；无遥测 |
| 零账号 | 不做登录，不需要手机号 |
| 只读原始数据 | 导入时只读不写源文件；不修改微信/QQ 目录（写回是独立开关） |
| 访问最小化 | 不申请通讯录/短信/定位；Android 只申请 `READ_MEDIA_IMAGES` |
| 可审计 | 所有写操作落 ops，可追溯「这张图什么时候从哪来的」 |
| 导出透明 | 备份包内含 `manifest.json`，写明来源与时间 |

## 15. 演进路径

| 如果…… | 就…… |
|---|---|
| WebView 网格在手机上卡 | Android 换 Compose 重写列表，后端 API 不动 |
| Python 打包太难受 | 桌面壳换 Tauri，后端换 Rust；**库格式不变，数据不受影响** |
| 同步冲突太多 | 退回「单设备 + 手动导出/导入」，或引入真正 CRDT |
| 微信解密成功 | 新增 `wechat_dat` 适配器，其余不动 |
| 想要多设备实时 | 加本地同步服务（FastAPI 已有），Syncthing 变可选 |

**这套架构最大的保险是库格式**：无论前端换成什么，`blobs/` + `ops/` + 一份 schema 文档，十年后拿 Python 三十行也能读出来。
