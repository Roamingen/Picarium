## 1. 技术栈定版

### 1.1 结论

```
┌──────────────────────────────────────────────────────────┐
│  UI 层   Vue 3 + TS  （两端同一套，可整体替换）             │
├──────────────────────────────────────────────────────────┤
│  壳层    Tauri 2（Windows: WebView2 / Android: WebView）   │
├──────────────────────────────────────────────────────────┤
│  核心    stickerbox-core  （纯 Rust crate，零 UI 依赖）     │
│          库 / 索引 / 搜索 / 去重 / 同步 / 导入 / 剪贴板       │
├──────────────────────────────────────────────────────────┤
│  数据    blobs（内容寻址）+ SQLite + ops 日志 + manifest     │
└──────────────────────────────────────────────────────────┘
```

**一条铁律：核心是一个独立 crate，不依赖 Tauri。**
壳可以换（Tauri → 原生 Win32 → slint），UI 可以换（Vue → React → 甚至命令行），核心不动。这就是抗时间的做法——把易变的东西关在笼子里。

### 1.2 你机器上的实测

| 依赖 | 状态 | 说明 |
|---|---|---|
| Rust | ✅ 1.93.1（msvc） | |
| MSVC 链接器 | ✅ VS2022 Community，`link.exe` 14.39 | Rust msvc 目标必需 |
| Node / pnpm | ✅ 24.13.1 / 10.28.2 | 前端构建 |
| WebView2 运行时 | ✅ 146.0.3856.97 | Windows 端必需，Win10/11 基本都自带 |
| JDK | ✅ 21.0.6 | Android 构建要求 17+ |
| Android SDK | ✅ platform 35 / build-tools 35 | |
| **Android NDK** | ❌ **未安装** | 需要装，约 1–2 GB，30 分钟 |
| **Rust Android targets** | ❌ **未安装** | `rustup target add aarch64-linux-android ...` |
| **tauri-cli** | ❌ **未安装** | `cargo install tauri-cli --version "^2"`，约 5–10 分钟 |

> 桌面端今天就能开工；Android 端要先补三样东西，约 1 小时环境配置。
> 另：我当前会话的沙箱禁止执行 `Program Files` 下的 `link.exe`，所以**我在这里编译不了**。要么你在本机终端跑构建，要么给我一次完整权限批准。写代码不受影响。

### 1.3 为什么不是 Python（以及为什么不是 Electron）

| 方案 | 单 exe | 常驻内存 | 冷启动 | 依赖 | 结论 |
|---|---|---|---|---|---|
| **Tauri 2** | ✅ 5–10 MB | 80–150 MB | < 0.5 s | 系统 WebView2 | ✅ 选它 |
| Python + 打包 | ⚠️ 60–90 MB | 150–300 MB | 1–3 s | 自带解释器 | ❌ 你说的对，环境依赖重 |
| Electron | ❌ 120 MB+ | 300 MB+ | 1–2 s | 自带 Chromium | ❌ 为一个贴图工具太重 |
| C# / WPF | ✅ 40 MB | 100 MB | 快 | .NET 运行时 | 🟡 只做 Windows 才考虑 |

更关键的是：**Tauri 让 Android 复用同一个 Rust 核心**，这在"两端逻辑一致"上省掉一半维护成本，也直接降低"两个库行为不一致"的风险。

### 1.4 退路（先想好，免得到时候慌）

| 如果 | 就 |
|---|---|
| Tauri Android 工具链太折腾 | 保留 `stickerbox-core`，用 **uniffi** 生成 Kotlin 绑定 + Compose 写手机 UI。核心仍然是那一份 Rust |
| WebView 网格在手机上卡 | 同上，换 Compose 列表 |
| Tauri 本身哪天不维护了 | 壳换成原生 Win32 或 slint，核心与数据格式不变 |

> 注意这三条退路**都不需要改数据格式**。这是设计目标，不是巧合。

## 2. 耦合面：只留 5 个接口

你的核心诉求是"不想和聊天软件底层打交道、不想被系统更新搞死"。那就把依赖面压缩到一张纸能写完的程度。

### 2.1 全量依赖清单（就这些）

| 平台 | 接口 | 出现年份 | 用途 | 变更风险 |
|---|---|---|---|---|
| Windows | 剪贴板 API（`CF_DIB` / `CF_HDROP` / `PNG`） | 1990s | 贴图出去 | 极低 |
| Windows | `RegisterHotKey` | 2000 | 唤起面板 | 极低 |
| Windows | 托盘图标 + 普通窗口 | 2000 | 常驻 | 极低 |
| Windows | 文件系统 | — | 库存储 | 极低 |
| Android | `ACTION_SEND` / `ACTION_SEND_MULTIPLE` | 2008 | 收图 | 极低 |
| Android | 文件系统（应用私有目录） | — | 库存储 | 低 |
| Android | `MediaStore`（只读，可选） | 2013 | 相册体检 | 中（权限政策常变，故设为可选功能） |
| 两端 | WebView | Win: 2020 / Android: 2014 | UI | 低 |

**与聊天软件的代码接触面：0 行。**
我们从不 import 任何微信/QQ 的 SDK，不读它们的目录，不 hook 它们。我们只跟**操作系统**说话：Windows 的剪贴板、Android 的分享意图。聊天软件只是"碰巧"是剪贴板和分享的另一个端点。

### 2.2 永不使用清单（写进 README，防未来的自己手痒）

| 不用 | 原因 |
|---|---|
| 无障碍服务（AccessibilityService） | 权限重、审核严、系统一改就废、容易被判定为恶意 |
| 悬浮窗（SYSTEM_ALERT_WINDOW） | 见第 5 节 |
| root / Shizuku / ADB 授权 | 用户门槛高，机型差异大 |
| hook / 注入 / 读其他 App 私有目录 | 法律与条款风险，版本一更新全废 |
| 自定义输入法 | 工程量翻倍，微信输入框也不接受图片 |
| 注册表深度定制 / 驱动 / 服务 | 卸载残留、杀软误报 |
| 第三方云 SDK（OneDrive/百度/阿里） | 账号体系、审核、接口变更，全是耦合 |

### 2.3 为什么这套"经得起时间"

- **接口老**：剪贴板和 `ACTION_SEND` 都活了 15 年以上，是系统里最不可能改的东西。
- **数据是文件**：库就是一个文件夹，最坏情况下用资源管理器也能把图片捞出来。
- **核心可替换**：壳、UI、甚至语言都能换，数据格式不变。
- **不自动更新**：默认关闭自动更新，版本由你决定什么时候升。工具类软件最怕"半夜自己升级然后挂了"。
- **依赖少**：Tauri 插件只用官方的窗口/托盘，剪贴板和多格式写入自己用 `windows` crate 写（约 200 行），不把命脉交给第三方插件维护者。

## 3. 数据格式（在 v0.1 基础上微调）

结构不变，只调整两处：

```
Picarium/
├── library.json          # {schema: 1, id, created_at, app_version}
├── library.db            # SQLite（可删，可重建）
├── blobs/ab/cd/<sha256>.<ext>
├── thumbs/ab/cd/<sha256>.webp
├── ops/<device>/<seq>.jsonl
├── inbox/  trash/  exports/
└── .stignore             # 给 Syncthing 用的忽略规则（顺手支持）
```

| 调整 | v0.1 | v0.2 |
|---|---|---|
| 中文检索 | jieba 分词后写入 FTS5 | **`tokenize='trigram'`**，SQLite 内置，2 字查询走 `LIKE` 兜底 |
| OCR | M1 必做 | **M2 才做**，用 `ort`（ONNX Runtime）+ PP-OCRv4 模型 |
| 分类 | 启发式 + CLIP | 不变，仍在 M2 |

**兼容承诺**（写进代码，不靠自觉）：

1. `library.json.schema` 单调递增；新版本能读旧库，自动迁移并**备份原库**。
2. 未知字段**原样保留**，不因旧版本读不懂就删掉。
3. 每个大版本发布前，用固定的 200 张样本库跑一次「导入 → 打标 → 搜 → 复制」回归。

## 4. 同步：三档方案

### 4.1 结论

| 档 | 方案 | 何时用 | 成本 | 推荐度 |
|---|---|---|---|---|
| **A** | **局域网直连**（PC 当服务端，手机主动连） | 每天回家自动同步 | 写 400 行 Rust | ⭐⭐⭐⭐⭐ 主方案 |
| **B** | **手动加密包**（导出一个 zip，任意方式搬运） | 出差、跨网络、应急 | 写 100 行 | ⭐⭐⭐⭐ 兜底 |
| C | 云盘文件夹（OneDrive/Syncthing） | 你非想用云 | 0 行（格式天然兼容） | ⭐⭐ 不推荐，但不阻止 |

**M1 先完全不做同步**（单机 PC 版）。同步是 M4 的事，先让快贴跑顺。

### 4.2 先回答"两个库"的担心

你说担心"电脑一关就没法同步，只能维护两个库"。**在日志复制模型下，不存在"两个库"，只有"两个副本"。**

```
时间线
─────────────────────────────────────────────────────────────
周一 09:00   手机在家 Wi-Fi，同步 → 两边都是 882 张
周一 10:00   你出门，手机离线
周二 12:00   手机收到 3 张新表情 → 只写进手机的 ops/phone-xxx/
周三 20:00   电脑上手动加了 5 张 → 只写进 PC 的 ops/pc-xxx/
周五 19:00   手机回家连上 Wi-Fi → 交换 ops → 两边都是 890 张
─────────────────────────────────────────────────────────────
```

- 离线期间，**两端各自都是完整可用的库**，不是一个"残缺副本"。
- 合并 = 交换两份日志，没有主从、没有覆盖。
- 真正需要担心的只有"删除"——所以删除是墓碑（保留 30 天可撤销），且**不会**把对端文件直接删掉。

换句话说：**手机不需要电脑在线才能用；它只是"晚一点知道电脑上发生了什么"。**

### 4.3 局域网协议（A 档）

```
配对（一次性）
  PC: 显示二维码 / 6 位数字，内含 {host: 192.168.x.x:7391, token: 32 字节}
  手机: 扫码 → 存下 host + token

每次同步
  1. 手机 POST /sync/hello   {device, state: {pc-xxxx: 128, phone-yyyy: 42}}
  2. PC   返回               {state, ops_after}
  3. 手机 GET  /sync/ops?after=...     ← 拉 PC 的新日志（JSONL 流）
  4. 手机 POST /sync/push              → 推自己的新日志
  5. 双方比对缺失的 blob 哈希，逐个 GET /blobs/{sha}（支持 Range 断点续传）
  6. 各自应用、写库、原子落盘
```

要点：

- **HTTP + JSON + 纯文件**，没有自研协议，出问题用 curl 就能查。
- **幂等**：`applied_op(dev, seq)` 主键去重，重复同步一百次结果一样。
- **可中断**：拉到一半断网，下次从 `after` 继续。
- **只读 TCP 一个端口**，不开放文件系统，PC 端不需要管理员权限。
- 发现设备：二维码优先（最可靠），mDNS 作为可选项（HyperOS 常屏蔽组播）。

### 4.4 手动加密包（B 档）

```
导出：stickerbox export --since 2026-10-01 -o sync-20261028.stbx
导入：stickerbox import sync-20261028.stbx
```

- 就是一个 zip：`manifest.json`（含每张图的 sha256）+ `ops/` + `blobs/`。
- 可选密码加密（AES-256-GCM），防止文件传输助手/网盘里的图片被别人看到。
- 适合：出差带笔记本、换手机、异地备份。**不依赖任何云、任何第三方。**

### 4.5 云盘（C 档）：OneDrive 四问四答

你问的四个点，逐个说清楚：

| 问题 | 结论 |
|---|---|
| **国内裸连稳定吗** | 个人版 OneDrive **不稳定**。它是国际出口，网页版经常很慢或间歇性打不开，客户端常见"一直正在同步"、OAuth 登录失败。企业版（世纪互联）稳定得多，但要有企业账号。**不建议当主通道。** |
| **有审核机制吗** | 有。微软对所有 OneDrive 内容做自动化扫描（CSAM、恶意软件、版权投诉）。普通表情包（含动漫截图、影视截图）触发版权投诉的概率**极低但不为零**；账户被锁是极小概率但影响极大。 |
| **会丢数据吗** | 真正的风险不是审核，是**同步语义**：文件夹同步会把一端的"删除"同步到另一端；个人版版本历史只有 30 天；账户被锁时文件取不出来。 |
| **那能用吗** | 能，但只建议做**单向定期备份**（PC 导出加密包 → 传到云盘），不做双向实时同步。 |

> 另外说一句：我们的库格式**天然兼容**云盘文件夹同步（blobs 内容寻址不会冲突、ops 按设备分目录不会冲突）。所以哪天你真想开云同步，不需要改一行代码——这也是格式设计带来的自由度。只是**默认不推荐**，因为网络和账号不是你我能控制的。

### 4.6 为什么不直接上 Syncthing

Syncthing 很成熟，零代码。但它引入的是另一个"需要维护的东西"：Android 后台被杀、耗电、版本升级、端口发现。你要的是"少维护"，那自己写 400 行 HTTP 同步，反而比伺候一个第三方同步器更省心。

## 5. 手机端：为什么不做悬浮窗

### 5.1 悬浮窗的账

| 维度 | 悬浮窗 | 分享到 App |
|---|---|---|
| 权限 | 需"显示在其他应用上层"，HyperOS 还有额外开关 | 无 |
| 稳定性 | 被系统杀、被厂商限制、焦点抢不到 | 系统级，几乎不会坏 |
| 能不能拖进微信 | **不能**（跨应用拖拽安卓不支持） | — |
| 能不能直接发 | 不能，只能复制，而微信不收剪贴板图片 | 系统分享直接发 |
| 维护成本 | 高（窗口生命周期、触摸穿透、多任务切换） | 极低 |
| 实际省几步 | 1–2 步 | 0 |

**结论：不做。** 悬浮窗看起来酷，但它解决不了"微信不接收粘贴图片"这个根本问题——最后还是要走分享。花大成本只省 1 步，不值得。

### 5.2 真实流程与步数（先接受，再优化）

**收图（2 步）**

```
微信长按图片 → 转发/分享 → [Picarium]  ← 声明一个无界面 Activity，存完弹 toast 自动关闭
```

**发图（4 步，这是系统下限）**

```
打开 Picarium → 选图 → 分享 → 微信 → 选联系人
```

> 说明：微信 Android 输入框不支持粘贴图片，所以"复制→粘贴"这条路走不通。要发图，只能让微信作为分享的接收方。这不是我们的设计问题，是平台事实。

### 5.3 便宜又有效的减负

| 手段 | 成本 | 收益 |
|---|---|---|
| 无界面分享接收 Activity（存完即退） | 30 行 | 收图从 4 步降到 2 步 |
| 桌面图标长按 → 「存图」「最近」快捷方式 | 20 行 | 少点一次 |
| 最近使用放在首屏第一行 | 0 | 发图常用路径最短 |
| 通知栏"最近 3 张"常驻通知 | 50 行 | 聊天中一拉就能分享（可选，默认关） |

## 6. 微信存量：说人话

上一轮我那句"愿意手动补多少"没说清楚，道歉。重新讲：

**微信收藏的表情，存在微信自己的加密文件里，我们已经决定不碰。** 所以那 1464 张想进你的库，只有两条路：

| 路 | 做法 | 代价 |
|---|---|---|
| A · 放弃 | 不管它们。以后聊天时看到好用的，长按"复制"，库自动收一张 | 0，但老表情要重新遇到才会进库 |
| B · 手动搬 | 在微信里逐张"另存为"到电脑，再拖进库 | 约 5 秒/张 × 1464 ≈ **2 小时**，且很枯燥 |

**我的建议：选 A。** 表情包的价值在于"最近常用"，两年没用过的老表情，搬进来大概率也不会用。真遇到怀念的，随手复制一次就进来了。

这条不影响任何功能，只是让你对"库里的数量"有个合理预期：**开局 882 张（QQ），不是 2300 张。**

## 8. 需要你点头的 4 件事

| # | 决策点 | 我的建议 | 备选 |
|---|---|---|---|
| 1 | 桌面端用 Tauri 2 + Rust + Vue | ✅ | Electron / 纯 Win32 |
| 2 | 手机端也用 Tauri（同核心、同 UI） | ✅ 先试；工具链不顺就换 uniffi + Compose | 直接上 Kotlin 原生 |
| 3 | 同步：局域网直连为主 + 加密包兜底，**不接云** | ✅ | 加 Syncthing 支持 |
