⑧ 拖拽排序 · 构思
1长按 340ms：轻震 + 卡片微缩（lift）；原地松手 = 进多选，不松手直接拖 = 排序。
2其余卡片用 FLIP 让位，虚线框就是落点。
3置顶组固定前区，不参加这层排序（置顶顺序在图库置顶条里拖）。
松手 → set_group_order 保存 → toast「顺序已保存」。
本轮只改 docs/mock/，没有动 src-tauri/ui/ 和 Rust。
拖拽为什么现在没效果（读 mobile.js:860-930 / 1441-1465 的结论）
  • .folder 没有 touch-action：pointermove 里的 preventDefault() 拦不住 WebView 的原生滚动；手指一移，浏览器发 pointercancel，1465 行只 resetHold，不清 dragCtx / ghost，长按在拖动开始前就被打断。
  • 落点用了后端顺序：updateFolderDrag 按 S.groupList 算落点（912 行），但 renderFolders 渲染的是「置顶优先」顺序（342 行）；两个顺序不一致，落点会跳。置顶组更直接——renderFolders 按 S.pinned 排，改了 S.groupList 也看不出来。
  • 每次移动整表重建：renderFolders(true) 重建 DOM（918 行），旧卡片上的 pointer capture 丢失；ghost 留在 body 上没人收。
  • 修法：给 #folders 挂非 passive 的 touchmove，armed 后 preventDefault 阻断滚动（或拖动期间给拖动层 touch-action:none）；pointercancel 走 endFolderDrag 清 ghost；落点用渲染顺序（renderedOrder）算；FLIP 只改 transform，不重建。
实现时注意
  • group_list 现在只返回 count，没有 bytes；详情头如果继续用 list_assets(limit 500) 的 items.length 当张数，超过 500 会少。建议 group_list 补 bytes（求和），头部直接用后端值。
  • remove_group(delete_assets=true) 走 self.remove() = 进 trash/，是软删除；文案统一说「回收站 / 可恢复」，别写死 7 天（保留天数 7/30/90 可设）。
  • 并入 = add_to_group(目标) 之后 remove_group(源, delete_assets:false)；目标列表排除自己 + 收藏夹（收藏夹是 starred 标记，不是真分组）。
  • 收藏夹在选择态直接隐藏；四个按钮对它都没意义。长按多选与拖动排序靠 8px 位移阈值区分，别让浏览器的长按选中/上下文菜单抢事件。
