# 20 · 安卓架构设计

> 2026-10-31 · 回答三个问题：要不要新目录、能不能在电脑上测、代码怎么分

## 1. 要不要新开项目目录？

**不新开仓库**，但建议把现有结构标准化一次：

```
repo/
  crates/core/          # 纯 Rust：索引、blob、搜索、排序、导入
  ui/                   # 共享前端：index.html / app.js / style.css
  ui/mobile.css         # 移动端覆盖（新增）
  src-tauri/            # 唯一的 Tauri 壳（现在的 app/ 改名）
    src/
      main.rs
      platform/         # 见第 3 节
    capabilities/
      desktop.json
      mobile.json
    plugins/share/      # Android Kotlin 插件（Tauri mobile plugin）
    gen/android/        # `tauri android init` 生成，不手写
  scripts/              # accept.ps1 / perf.ps1 / android-setup.ps1
```

- `tauri android init` 默认在 `src-tauri/` 下生成 `gen/android`，所以**不要**另起一个 `android/` 应用目录；
- 桌面和安卓共用同一个 Tauri 工程，用 `cfg(target_os)` + 不同 capabilities 区分能力；
- 若想先试验、不打扰桌面，可开一个 `mobile` 分支跑通，再合回。

**不建议**另建 `mobile/` 独立工程：会产生两套 tauri.conf、两份依赖、两套权限，UI 一改就要同步两边。

## 2. 能不能在电脑上运行测试？

分三层：

| 层 | 在哪测 | 说明 |
|---|---|---|
| Rust core（索引/搜索/导入） | 电脑 `cargo test` | 纯 Rust，完全不需要安卓 |
| 移动端 UI 布局 | 电脑上跑现有桌面壳，加 `?platform=android` 模拟参数 | 窗口拉到手机比例即可看 grid/底栏/多选；不需要模拟器 |
| Android 系统能力（分享进/出、SAF、权限） | 电脑上的 Android 模拟器（AVD）或真机 | 必须 `tauri android dev`，这部分无法在 Windows 壳里验证 |

建议开发顺序：UI 先在电脑上调到满意 → 模拟器只验证系统边界。

## 3. 分层

```
┌──────────────────────────────────────────────┐
│ UI（同一套 HTML/CSS/JS）                      │
│  - 桌面：键盘、右键、多选、拖拽、悬浮面板      │
│  - 安卓：底部导航、长按多选、分享、无 hover    │
└───────────────┬──────────────────────────────┘
                │ invoke / event
┌───────────────▼──────────────────────────────┐
│ commands（共享）                              │
│  list_assets / get_asset / import_paths /     │
│  batch_* / update_asset / stats …             │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│ platform traits（按目标实现）                 │
│  Clipboard · Share · FilePick · OpenFile ·    │
│  Hotkeys · Tray · RecycleBin · Singleton      │
│  desktop.rs（Win32）  android.rs（JNI→Kotlin）│
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│ crates/core（纯 Rust，100% 复用）             │
│  Library / Asset / blob / search / orders     │
└──────────────────────────────────────────────┘
```

- 桌面专属 trait 在 Android 给 no-op 实现（Hotkeys/Tray/RecycleBin/Singleton）；
- `Clipboard` 在安卓只做「复制文件路径给系统」的降级，图片复制不可靠，主出口是 Share；
- `FilePick` 桌面返回路径，安卓返回 content URI 的缓存副本。

## 4. 安卓系统边界（Kotlin 插件）

`plugins/share` 暴露三个命令 + 一个事件：

| 名称 | 作用 |
|---|---|
| `share_files(paths: Vec<String>)` | 用 `FileProvider` 生成 content URI，`ACTION_SEND_MULTIPLE` 拉起分享面板 |
| `pick_images()` | `ACTION_OPEN_DOCUMENT`（多选），把 URI 复制到 `cacheDir/inbox/<uuid>`，返回本地路径 |
| `pick_folder()` | 视系统能力降级；不行就提示「安卓请用多选图片」 |
| `share-in` 事件 | Manifest 里 `SEND/SEND_MULTIPLE` + `image/*`，MainActivity 收到后复制到 inbox，emit 给前端 |

导入统一走 Rust 的 `import_paths`，因为拿到的是缓存里的真实路径。

## 5. 存储与缩略图

- 库根目录：`app_data_dir()/StickerBox`（和桌面同一套 `index.json` + `blobs/ab/cd/` + `thumbs/`）；
- 缩略图在导入时生成，前端用 asset 协议（scope 只放开库目录），不用自定义 `thumb://`；
- 分享进/出的临时文件放 `cacheDir/inbox`，导入成功或过期后清理。

## 6. 移动端 UI 设计

不包含键盘和快捷键，其余尽量同构：

- 首页：搜索 + 分组横向 chips + 网格（复用虚拟滚动）；
- 底部导航：全部 / 分组 / 最近 / 设置；
- 点按卡片 = 预览大图；预览页按钮：分享、复制文件、收藏、删除；
- 长按 = 进入多选，顶部显示「已选 N」+ 分享/分组/标签/删除；
- 没有右键、hover、拖拽排序；分组移动用「批量 → 加入分组」；
- 设置页只保留：主题、网格大小、虚拟滚动、最近上限、导出/导入、关于。

## 7. 数据流

**分享进入**

```
微信 → ACTION_SEND(image/*) → MainActivity
     → 复制 URI 到 cache/inbox
     → emit share-in(paths)
     → Rust import_paths(paths, source="share")
     → 刷新列表 + toast「已收 N 张」
```

**分享出去**

```
用户选 N 张 → 分享按钮
  → Rust 收集原文件路径
  → Kotlin share_files(paths)
  → FileProvider content:// → ACTION_SEND_MULTIPLE
  → 微信/QQ 收到原图（GIF 保留动画）
```

## 8. 黑名单（与桌面共用配置）

`clipboardBlacklist` 是桌面剪贴板轮询用的；安卓没有后台剪贴板读取，**不生效也不显示**。
设置页按平台隐藏该区块，避免误导。

## 11. 会不会污染手机相册？

**默认不会。** 关键在存储位置和分享方式：

| 操作 | 文件去了哪 | 相册可见？ |
|---|---|---|
| 分享图片进 StickerBox | 复制到应用私有目录 `files/StickerBox/blobs` | 否 |
| SAF 选图导入 | 读 `content://` 后复制到私有目录 | 否（原图不动） |
| 从 StickerBox 分享出去 | 私有文件 → `FileProvider` 临时 `content://` | 否（不写 MediaStore） |
| 缓存/临时文件 | `cacheDir/inbox`，导入或分享后清理 | 否 |
| 用户主动「保存到相册」（未来可选） | MediaStore `Pictures/StickerBox` | 是（仅此一种，且需用户点） |

实现约束：

- 不申请 `READ/WRITE_EXTERNAL_STORAGE`、不申请 `MANAGE_EXTERNAL_STORAGE`；
- 不调用 `MediaScanner`、不往 `MediaStore` 插记录；
- 导入用系统选择器（Android 13+ 用 Photo Picker），只拿临时读权限；
- 分享用 `FileProvider` + `FLAG_GRANT_READ_URI_PERMISSION`，对方读的是临时 URI，不是相册条目；
- 启动时和导入后清理 `cacheDir/inbox` 里超过 24 小时的文件。

唯一可能让用户觉得「相册被污染」的情况，是微信/QQ 自己把收到的图存进它的聊天缓存或相册——那是接收方的行为，不是 StickerBox 写的。
