## 4. 下一步（只做第一批）

**第一批建议：入库前做真正的图片校验，堵住「垃圾字节也能进库」。**

- 背景：测 12 MB 上限时，桥只按 ext 校验，`import_media_bytes` 里 `image::image_dimensions(...).unwrap_or((0,0))` 把解码失败吞成了 0×0，结果一段垃圾字节以 `big.gif` 进了真实库（已删，见事故记录）。这是当前最实在的数据风险。
- 目标：`import_media_bytes` 在 `image_dimensions` 失败、或宽高为 0、或像素数超过阈值（比如 1 亿像素）时返回错误；桥把该错误映射成 400「图片内容无法解码」。同时确认合法 GIF/WebP/PNG/JPG 全部不受影响。
- 涉及文件：`crates/core/src/lib.rs`（`import_media_bytes` 与两条单测）、`src-tauri/src/bridge.rs`（错误文案/测试）、必要时 `docs/28` §10。
- 验收方式：`cargo test -p stickerbox-core`；`cargo test -p stickerbox --lib bridge::`；curl 一段垃圾字节 → 400 且 `index.json` 资产数不变；真实 GIF → 200。
- 预计风险：全图解码大图会吃 CPU/内存，建议只用 header 解尺寸 + 像素上限，不做完整解码；别把 0×0 的合法动图误杀（先抽查现有库里 0×0 资产）。

后续（各一行）：

- 第二批：P3 剩余「token/端口可配」——扩展加 options 页存 `chrome.storage.local`，桌面端从 `settings.json` 读并在设置页暴露；先出 HTML 预览。
- 第三批：右键菜单补「下载到本地」；扩展 popup 显示桥连接状态 / 版本不匹配提示。
- 桥对不可解码内容的宽松策略，和「导入 0 字节」一起在第一批收掉。

## 6. 已知坑（会重复踩的）

- headless Chrome 157 **不注入 unpacked 扩展的 content script**（`--load-extension` 无效），页面钮只能用「把 `dist/content.js` 注入本地页 + stub `chrome.runtime`」的 DOM 用例验；真实链路必须让用户在 `chrome://extensions` 重载并刷新 B 站页。
- B 站评论在开放 Shadow DOM（`<bili-comments>`）里，且 hover 有遮罩层：`document` 的 `pointerover` 目标是宿主，必须用 `composedPath()` + `elementsFromPoint` 穿透，按坐标补判。
- 扩展 `MAX_BYTES` 与桥 body 上限是两道闸：body 收的是 base64，48 MB 只装得下 ~35 MB 原图；data URL 还会再膨胀 4/3，32 MB 图在下载路径可能失败（失败会走顶部提示，必要时改 offscreen）。
- `scripts/release.ps1` 会 `Stop-Process` 正在跑的 App；装完要重新起 `--tray` 再验 `/ping`。
- 桥的 token 是硬编码，两端改要同时改；端口 17800 被占用时只告警，桥不可用。
- 装机版旧、扩展新的组合会出现「复制为文件其实只入库」——已用 `/copy` 404 文案兜底，但排查时先看 `/ping` 版本。
- `.demo/` 已 gitignore：截图、CDP 脚本、DOM 测试都放这里，不要入库。
